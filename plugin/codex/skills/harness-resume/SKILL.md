name: harness-resume
description: Resume a Stagekeeper item in Codex after owner approval or a confirmed client switch.
---

Read the installed sibling `../harness-run/SKILL.md` completely and follow it. Resume uses the
same shared server ledger and explicit foreground ownership; never reconstruct a cursor from
chat history. Resolve installed helpers through the actual skill path and read this checkout's
harness.json and docs/harness/codex-runbook.md.

When a key is supplied, prepare a new foreground session after the previous owner's actual
quiescence and run `next --session <id> --key <KEY>`. Never inherit local policies from the other
client. Read board_get and check approved planCommit/planPath and present files. Server approval
is durable across clients, but model history and uncommitted files in a different clone are not.
Preserve the actual open AgentRun's step/receipt/entry/agentRunId; do not close it, clone it or
record success without doing and verifying the current work. New entries can legitimately open
new runs under the existing cap. Follow dispatch/wait/accept/done, then query pipeline again.

If a same-client foreground session from this main loop is still owned and active, check and
reuse it rather than nested prepare. Do not adopt a watch or another caller's session just from
an ID. Codex automatic watch/resume signals are not supported by this release. An explicit
owner continue after handoff resumes without outcome, after checking the actual committed file.
