# {{project.name}} — 파이프라인 런북

개발 작업은 아래 파이프라인으로 돈다. 이 문서는 그 절차서다 — **상태는 담지 않는다.**
작업 상태의 진실은 하니스 서비스의 DB이고, 이 저장소에는 코드와 그 옆의 기록만 있다.

## 문서 지도

| 문서 | 역할 |
| --- | --- |
| (웹) 백로그·보드·결재함 | 할 일 원장과 작업 상태 기계. 전이 규칙·정지 규칙·인수 조건이 서버와 화면에 있다. 편집은 웹, 읽기는 `mcp__harness__*` 도구 |
| `harness.json` | 워크스페이스·담당 에이전트·검증 명령. 에이전트 정의를 생성하는 입력 |
| `docs/plans/<항목ID>.md` | 항목별 구현 계획서 |
| `docs/plans/verification-paths.md` | 계획서 검증의 필수 경로 카탈로그 — 항목 성격이 검사를 정한다 |
| `docs/agents/<행위자>/` | 행위자별 활동 보고서 — 보드가 담지 않는 상세. 규약은 그 안 `README.md` |
| `.claude/agents/*.md` | 에이전트 정의 (역할·도구·제약). `/harness:init`이 생성한다 |

## 파이프라인 절차 — 메인 루프가 실행한다

상태의 정의와 전이 권한은 서버의 상태 기계가 진실이다. 여기는 실행 순서만 적는다.

1. `pm` 디스패치 → `board_propose`로 `승인대기` 기록, 미결 현황 보고
2. **게이트①** — 사용자가 웹 결재함에서 `계획지시` 도장을 찍는다 (사용자만 할 수 있다)
3. 담당 dev 디스패치 → `docs/plans/<항목ID>.md` 계획서만 작성, `plan_submit` 후 `검토대기`
4. 메인 루프가 카탈로그(`docs/plans/verification-paths.md`)에서 필수 경로를 확정하고, `reconciling-proposals-with-codebase` 스킬로 검증·편집한다. 자기 라운드가 무소득이 되면 `plan-verifier`를 디스패치해 **독립 무편집 패스**를 받는다. 클린 패스가 나오면 `validation_record`로 한 줄 남긴다 — **클린 패스일 때만** 쓴다(형식: `클린 패스 (YYYY-MM-DD, 무편집 N라운드)`). 결재함이 이 줄의 존재만으로 판정하므로 아닌데 쓰면 거짓 통과가 된다. 라운드 종료마다 `git status`로 트리 청결을 검산하고(검증자의 무수정 준수를 보고가 아니라 직접 확인), 검증 라운드 기록은 `docs/agents/main-loop/<항목ID>.md`에 남긴다
5. **게이트②** — 사용자가 웹 결재함에서 `구현승인` 도장을 찍는다
6. 담당 dev 디스패치 → 구현, `docs/agents/<자기이름>/<항목ID>.md`에 구현 보고, `report_submit` 후 150자 `result` 요약과 함께 `완료`. **백로그에서 항목을 빼는 것은 서버가 한다**
7. 메인 루프가 완료를 인수한다 — 아래 **인수 다섯 조건**을 직접 재현한다. 다섯 다 에이전트의 보고가 아니라 직접 본 것이어야 한다.
   1. 변경 파일 목록 ↔ 계획서 「고칠 파일」
   2. diff ↔ 계획서 「구현 스케치」
   3. 검증 명령 직접 재실행
   4. 백로그에서 그 항목이 제거됐는지 확인 (웹 또는 `backlog_list`)
   5. `result`가 가리키는 상세 기록(`docs/agents/<행위자>/<항목ID>.md`)의 실재 확인

   인수한 계획서에 「범위 밖 의존」이 있으면 백로그 후보로 사용자에게 제시한다. **등재는 사용자가 웹 백로그에서 한다** — 백로그 편집은 웹 전용이라 에이전트도 메인 루프도 쓸 수 없다. 등재 안 된 후속은 pm의 입력에서 증발한다
8. `doc-auditor` 디스패치 → 감사 보고를 사용자에게 전달하고, **메인 루프가 `docs/agents/doc-auditor/감사기록.md`에 이어 붙인다**(그 에이전트에겐 쓰기 도구가 없다). `feature-scout`도 같다

## 운영 규칙

- **디스패치는 메인 루프만 한다.** 파이프라인 에이전트끼리는 서로 호출하지 않으며, 에이전트 정의에 Task(Agent) 도구를 주지 않는다. 이유: 피호출 에이전트는 호출자의 제약이 아니라 자기 도구 구성으로 돌기 때문에, Task 하나가 모든 도구 제약의 우회로가 된다.
- **커밋하는 것은 계획서·행위자 기록·코드뿐이다.** 보드 상태는 서비스에 있으므로 커밋할 것이 없다. 브랜치는 `{{board_branch}}`.
- **게이트①②는 사용자만 연다.** 어떤 에이전트도, 메인 루프도 대신 전이하지 않는다 — 에이전트 토큰에는 그 도구가 등록되어 있지 않다.
- 문서 간 규칙이 충돌하면: 상태·전이·인수는 서버의 상태 기계와 이 문서의 7단계, 에이전트 행동은 해당 에이전트 정의 파일이 이긴다. 이 문서는 색인과 실행 순서만 맡는다.
