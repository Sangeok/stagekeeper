# plans

보드 항목 하나당 계획서 하나. 담당 에이전트가 **코드를 고치기 전에** 쓰고,
사용자가 읽고 승인한 뒤에야 구현이 시작된다.

## 파일명

`<항목ID>.md` — 보드의 항목ID를 그대로 쓴다 (`BUG-05.md`, `FEAT-01.md`).

에이전트가 보드를 읽고 경로를 **계산**할 수 있어야 하므로 날짜나 제목을 붙이지 않는다.

## 절 구조

`template.md`가 단일 출처다. 에이전트는 계획서를 쓰기 전에 그 파일을 읽는다.

## 수명

`active/`·`completed/` 분리를 두지 않는다. 항목의 상태는 **하니스 서비스에만** 있다 —
파일 위치가 상태를 나타내면 둘이 어긋날 수 있고, 에이전트에게는 파일을 옮길 도구가 없다
(`Bash`는 읽기·검증 전용이고 삭제 도구가 없다).

`보류` 후 계획을 다시 쓸 때는 같은 파일을 **덮어쓴다.** 막힌 이유는 보드의 `result`(150자 요약)와
`docs/agents/<행위자>/<항목ID>.md`(상세)에 남으므로 기록이 두 곳에 필요하지 않다.

계획서는 **현재 계약**이라 하나만 유효해서 덮어쓴다. 반대로 `docs/agents/` 보고서는 **누적 기록**이라
덮어쓰지 않고 이어 붙인다 — 두 폴더의 규칙이 다른 이유다.

## 서비스와의 연결

계획서를 쓴 뒤 커밋하고 `mcp__harness__plan_submit({ key, path, commit })`으로 위치를 기록한다.
그 기록이 있어야 `검토대기`로 넘어갈 수 있다 — 서버가 순서를 강제한다.
