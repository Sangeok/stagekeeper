# {{project.name}} — pipeline runbook

Development work runs through the pipeline below. This document is the procedure. **It holds
no state** — the state lives in Stagekeeper. This repository holds the code and the records
next to it.

## The cycle — run by the main loop

The definition of each state and who may change it is the server's state machine. This is the
order of execution only.

1. Dispatch `pm` → it records a `proposed` item with `board_propose` and reports what's open
2. **Gate 1** — you request the plan in the web inbox (only you can)
3. Dispatch the assigned dev → it writes `docs/plans/<KEY>.md` only, calls `plan_submit`,
   moves the item to `in_review`
4. The main loop verifies: pick the required paths from the catalog
   (`docs/plans/verification-paths.md`), then verify and edit with the
   `reconciling-proposals-with-codebase` skill. When your own round finds nothing, dispatch
   `plan-verifier` for an **independent no-edit pass**. On a clean pass, write one line with
   `validation_record` — **only on a clean pass** (format:
   `clean pass (YYYY-MM-DD, N rounds, no edits)`). The inbox judges by the presence of that
   record alone; writing it otherwise is a false pass. After every round, check the tree is
   clean with `git status` (verify the verifier's no-edit promise yourself, not from its
   report). Keep the round log in `docs/agents/main-loop/<KEY>.md`
5. **Gate 2** — you approve implementation in the web inbox
6. Dispatch the assigned dev → it implements, writes `docs/agents/<itself>/<KEY>.md`, calls
   `report_submit`, moves to `done` with a result under 150 characters. **Removing the backlog
   entry is the server's job**
7. The main loop accepts — reproduce the **five acceptance checks** yourself. All five come
   from what you saw, not from the agent's report.
   1. Changed files ↔ the plan's "Files to change"
   2. Diff ↔ the plan's "Implementation sketch"
   3. Run the verify command yourself
   4. Confirm the backlog entry is gone (web, or `backlog_list`)
   5. Open the report the `result` points to (`docs/agents/<actor>/<KEY>.md`) and confirm it exists

   If the accepted plan lists out-of-scope dependencies, present them to the owner as backlog
   candidates. **Adding them is the owner's job, in the web backlog** — editing the backlog is
   web only; neither agents nor the main loop can. A follow-up that isn't added vanishes from
   pm's input
8. Dispatch `doc-auditor` → hand its report to the owner, and **the main loop appends it to
   `docs/agents/doc-auditor/audit-log.md`** (that agent has no write tool). Same for
   `feature-scout`

## Rules

- **Only the main loop dispatches.** Pipeline agents never call each other, and no agent
  definition gets the Task (Agent) tool. Reason: a called agent runs with its own tool set,
  not the caller's limits, so one Task call is a bypass for every tool restriction.
- **Commit plans, reports, and code. Nothing else.** The board's state lives in the service,
  so there's nothing of it to commit. The branch is `{{board_branch}}`.
- **Only you open the gates.** No agent and no main loop does it for you — the agent token
  doesn't have the tool.
- When documents conflict: states, transitions, and acceptance follow the server's state
  machine and step 7 above; agent behavior follows the agent's definition file. This document
  is the index and the order of execution, nothing more.
