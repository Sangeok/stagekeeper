# 파이프라인 정의와 실행

파이프라인은 같은 종류의 정의다. 다른 정의에 포함되는 관계와 특정 실행의 시작점은
사용 맥락으로 결정되며 Main/Sub 필드를 저장하지 않는다. Default도 다른 정의에 포함할 수 있다.
포함은 저장된 정의를 참조하고 실행을 시작할 때 펼친다. 순환 참조와 중복 노드는 기존 규칙대로 거부한다.
중복 위치를 안내하되 자동 삭제·교체·중복 실행은 하지 않는다.

## 화면과 선택 규칙

Pipeline의 첫 화면은 이름과 펼친 단계 요약을 보여 주는 전체 목록이다. 검색하지 않아도
목록을 탐색할 수 있고 이름이나 단계 이름으로 좁힐 수 있다. 하나를 열면 해당 구성의
편집과 Run만 보여 준다. All pipelines로 목록에 돌아가며 Switch pipeline은 검색 전부터
전체 목록과 현재 선택을 보여 준다. Main/Sub 분류나 유형별 편집 탭은 두지 않는다.

선택은 `?pipeline=<id>`, 새 초안은 `?pipeline=new`로 표현하며 기존 `work` 문맥을 유지한다.
전환·목록 복귀·브라우저 뒤로가기에서 미저장 변경을 확인하고 저장 중 전환을 막는다.
새 정의 저장 후 같은 편집 화면에 머물고 보관 후 목록으로 돌아간다. 찾을 수 없는 정의는
다른 정의로 몰래 대체하지 않고 목록·전환 경로와 함께 안내한다.

Run rules 패널은
새 작업의 기본 선택과 유형별 예외를 담는다. Discover work와 Assign work는 일반 노드이며 별도 전역 스위치로 실행하지 않는다. 설정 변경은 편집 대상을 바꾸지 않는다.
규칙에 연결한 정의는 전체 개발 흐름을 유지해야 한다. 그 밖의 정의는 필요한 단계만 가질 수 있다.
모든 정의의 Run은 같은 패널을 열어 대상과 필요한 담당자를 선택한다. 작업 상세에서 진입하면 대상을 미리 선택한다.
작업을 생성하는 노드로 시작하는 정의는 대상 없이 실행할 수 있다. Run 패널에서 프로젝트 실행의 승인과
Stop new work를 제공한다. 중지하면 이후 발견·배정을 멈추며 이미 배정된 작업 실행은 유지한다.

## 작업 발견과 배정

`Discover work` (`discover-work`, 실행자 `work-discoverer`)는 근거가 있는 백로그 후보를 추가한다.
어느 위치에나 놓거나 생략할 수 있다. Assign work 앞에서는 배정 가능한 후보가 없을 때 실행하며,
작업 실행 중간과 끝에서는 해당 위치에 도달하면 실행한다. 노드가 없으면 숨은 발견 작업을 실행하지 않는다.
`Assign work` (`assign-work`, 실행자 `work-assigner`)는 작업이 필요한 단계보다 앞에 한 번만 놓는다.
후보 선택, 준비 상태 확인, 담당자 선택, 선택 근거 기록과 보드 등록을 수행한다. PM 노드는 없다.
백로그가 비어 있고 발견 노드가 배정 뒤에만 있으면 새 후보를 기다린다.

`PipelineWorkRun`은 보드 항목 생성 전 실행이며 프로젝트마다 열린 실행 하나만 허용한다.
`PipelineVersion`과 entry를 고정하고 첫 Assign work까지 실행한다. 배정 후 보드 항목의 `PipelineRun`은
그 뒤 단계에서 시작한다. 작업 유형의 Run rule이 있으면 그 대상의 작업 단계로 전달한다.
Assign work만 있는 정의도 Run rule 또는 기본 작업 파이프라인으로 연결할 수 있다.
작업 없이 끝나는 프로젝트 노드 실행은 입력이 바뀌거나 소유자가 다시 시작할 때까지 반복하지 않는다.
승인은 소유자와 entry를 확인하며 `approvals`에 승인자·시각·노드를 기록한다.
정의와 선택 기준을 수정하면 영향받는 미배정 실행을 닫고 다음 실행부터 새 버전을 사용한다.
이미 배정된 작업의 버전은 변경하지 않는다. `workPipelineId`는 실행 대상으로 선택한 정의이며,
없으면 Default를 사용한다. `workAutomationPaused`는 소유자의 명시적인 중지를 보존한다.

선택 기준 `selectionPolicy`는 Assign work를 소유한 정의와 실행 버전에 저장한다. 기본값은
출처와 담당 workspace가 있는 후보 중 생성 시각, 키 순서다. 완료·보류·진행 중 작업은 자동 후보에서 제외한다.
`assignment_context`는 실제 후보, 출처, 담당 workspace, 기준과 입력 해시를 반환한다.
에이전트의 `board_propose`는 현재 배정 실행, 동일 토큰, 최신 입력 해시와 정책, 실제 Source 인용,
모든 다른 적격 후보와의 비교, 준비 상태, 담당자 선택 이유와 미해결 사항이 없음을 검증한다.
자유문장의 판단이 사실임을 서버가 증명하지는 않으며, 에이전트는 없는 긴급성·효과·의존성을 만들어서는 안 된다.
불충분한 근거는 blocked로 기록하고 사용자 보완을 기다린다. 기록은 `BoardItem.selectionDecision`과
작업 상세의 Assignment decision에 남긴다. 열려 있는 작업은 최대 두 개이며 등록 transaction에서도 재검사한다.

## 실행 입력과 검증

`packages/core/pipeline/run-input.mjs`는 펼친 그래프의 순서·게이트·플랜 권한과 작업 입력 조건을 판정한다.
계획은 새 작업에서 시작한다. 구현은 제출된 계획을 요구하며 Verify 없이 시작하려면 검증 기록도 필요하다.
구현 단계 없는 구현 검증·QA·인수는 기존 구현 보고와 원래 계획이 있는 Done 작업에서 시작한다.
계획에서 구현 없이 구현 검증으로 넘어가는 구성은 실행하지 않는다.
진행 중인 실행이 있거나 보류된 작업은 새 실행을 시작할 수 없다.

`preparePipelineRun`은 소유권과 가용성을 확인한 읽기 전용 조회다. 펼친 구성의 해시와
대상 작업의 수정 시각을 반환한다. `startPipeline`은 프로젝트 쓰기 잠금 안에서 소유권,
가용성, 그래프 해시, 최신 작업, 수정 시각, 입력 조건을 다시 검사한다. 동일 대상의 동시 실행 요청은 하나만 성공한다.
저장되지 않은 편집은 실행할 수 없다. 시작 응답을 잃으면 재시도를 막고 작업을 확인하도록 안내한다.

## 저장과 증거

`BoardItem.currentRunId`는 현재 실행을 가리키고 `PipelineRun.boardItemId`는 모든 실행 이력을 보존한다.
실행마다 `createdAt`, 선택적 `startedBy`, `PipelineVersion`을 고정한다. 새 실행은 이전 실행이나 보고를 덮어쓰지 않는다.
기존 구현을 검사하는 실행의 `inputReportId`는 동일 작업의 성공한 개발 보고를 고정한다.
QA와 구현 검증은 현재 실행의 구현 보고가 없으면 이 입력 보고를 사용한다.
에이전트의 run/entry 결합은 현재 실행에서만 유효하다. 실행 중 정의를 수정해도 저장된 실행 판은 바뀌지 않는다.

단계가 끝나면 `pipeline-completed:<runId>` 이벤트를 기록한다. 이것은 인수 증거가 아니다.
`accept`가 없는 실행은 `acceptedAt`을 변경하지 않는다. 이미 인수한 작업을 재검증해도 인수를 취소하지 않는다.
종료된 실행 중 완료 이벤트가 확인되는 경우만 화면에 Run completed로 표시하며 그 외는 Run closed다.
검증 전용 실행 뒤에 구현을 다시 열면 필요한 단계를 가진 이전 실행 판 또는 프로젝트 기본 판으로
새 실행을 만든다. 완료된 검증과 원래 구현의 실행 기록은 보존한다.

## 스키마 적용

`20261031090000_contextual_pipeline_runs`는 현재 실행 포인터와 실행 메타데이터를 추가하고
기존 일대일 연결을 포인터로 채운 뒤 실행의 작업 ID 유일성만 제거한다. 기존 행·보고·승인·버전은 삭제하지 않는다.
새 코드 배포 전 migration과 Prisma client 생성이 필요하다. 여러 실행이 생긴 이후에는
예전 일대일 스키마로 되돌릴 수 없으므로 이전 앱 버전을 그대로 재배포하지 않는다.
통합 시험은 격리된 `stagekeeper_test_*` PostgreSQL에서 실행한다.

`20261031120000_pipeline_work_nodes`는 프로젝트 실행·선택 기록·선택 기준을 추가한다.
기존 Default의 전역 자동 설정은 새 정의와 실행 버전의 앞쪽 노드로 옮기며 과거 버전과 작업 실행은 보존한다.
아직 저장되지 않은 Default는 최초 생성 시 옛 설정을 반영한다. 이후 실행은 저장된 노드만 따른다.
배포 전에 migration과 Prisma 생성을 적용하고 플러그인 0.5.33 이상으로 업데이트한 뒤 init을 다시 실행한다.
기존 private 템플릿을 호환 어댑터로 읽어 새 실행자의 스텁과 단계에 연결한다. 옛 PM/Scout 식별자는
기존 실행 이력과 구형 템플릿을 읽기 위한 호환 경로에만 남는다.
