# 테스트 코드 작성 규칙

테스트는 변경한 동작이 계약을 지키는지 확인하고, 그 계약을 깨는 결함을 검출한다.
검증 범위는 변경 위험에 맞추며, 동작을 보존하는 리팩터링에도 유지할 수 있어야 한다.

적용 범위는 `src`, `packages/core`, `plugin`, `scripts`, `tests`의 새로 작성하거나
수정하는 테스트와 인수 사례다. 작성 기준은 이 문서, 파일의 위치·이름·소유권과
의존성은 [테스트 배치 규칙](./test-organization.md), 실행 명령·CI 연결·DB 안전
절차는 [검증 문서](./verification.md)를 따른다.

## 필수 규칙

### 1. 동작 계약을 검증한다

- 입력과 조건, 수행할 동작, 관찰 가능한 결과를 명시한다. 반환값·오류·저장 상태·
  화면·허용되거나 금지된 부수효과 중 해당 계약을 증명하는 결과를 검사한다.
- 기대값은 요구사항과 독립적인 사례에서 정한다. 검증 대상 함수를 다시 호출하거나
  구현의 분기를 복제해 기대값을 만들지 않는다. 공유 정책과 소비자의 연결을 대조하는
  검사는 무엇과 무엇의 일치를 보장하는지 명시한다.
- 테스트 이름이 실제 검증보다 넓은 보장을 주장하지 않게 한다. 정적 HTML의 버튼
  ID 검사는 구조를 확인하며, 포커스 복구는 이벤트 이후의 실제 포커스를 확인한다.
- 소스 문자열·AST·정확한 값 비교는 공개 API 경계, `server-only`, Action 노출,
  배포 manifest, 문구 잠금처럼 구조나 값 자체가 계약일 때 사용한다. 일반 동작
  테스트는 내부 변수명·JSX 계층·전체 클래스 문자열에 대한 의존을 줄인다.

### 2. 변경 위험에 맞는 테스트를 작성한다

- 새 동작, 버그 수정, 중요한 경계 변경을 보호하는 사례를 선택한다. 구현 파일이나
  함수마다 테스트를 기계적으로 추가하거나 같은 수준의 검증을 중복하지 않는다.
- 버그 수정은 가능하면 수정 전 실패와 수정 후 성공을 확인한다. 재현 환경을
  마련하지 못한 경우에는 검증한 대체 범위와 남은 확인 사항을 결과에 남긴다.
- 변경과 관련된 상태 전이, 권한, 입력 경계값, 오류 분기, 경합·복구를 우선한다.
  낮은 위험의 가역적 변경과 동작을 보존하는 리팩터링은 기존 관련 검증을 활용하고
  실제 누락이 있는 부분을 보완한다.
- 커버리지는 누락을 찾는 보조 지표로 사용한다. 테스트 개수나 커버리지 수치만으로
  검증의 충분성을 판정하지 않는다.

### 3. 증명할 성질에 맞는 환경을 선택한다

필요한 계약을 관찰할 수 있는 가장 작은 검증 범위에서 시작한다. 여러 모듈을
호출한다는 사실만으로 DB나 브라우저가 필요한 것은 아니며, 실제 저장·프레임워크·
OS 동작에 의존하는 성질은 해당 환경에서 확인한다.

| 검증할 성질 | 필요한 검증 |
| --- | --- |
| 순수 정책·상태 전이·입력 검증 | 기존 `node:test`로 입력·출력·불변식을 검사한다 |
| 서버 서비스의 분기·오류 처리·협력 계약 | 안정된 의존성을 주입해 반환값과 관찰 가능한 부수효과를 검사한다 |
| transaction·잠금·제약조건·rollback·migration | 안전 검사를 통과한 격리 PostgreSQL에서 실제 저장 결과를 검사한다 |
| 정적 UI·문구·링크·초기 disabled 상태 | 정적 렌더 결과를 검사한다 |
| 클릭·포커스·pending·늦은 응답 | 실제 DOM의 이벤트와 후속 상태를 검사한다. 실제 키보드 입력·클립보드 권한 등 브라우저 동작은 브라우저에서 확인한다 |
| 인증·Server Action·async Server Component·RSC 갱신의 연결 | fresh production build로 실행한 Next에서 실제 요청과 응답·화면·저장 결과를 검사한다 |
| 플러그인의 파일·프로세스·OS 권한 | 격리된 실제 파일·프로세스와 해당 OS에서 검사한다 |

mock은 DB·HTTP·시계·외부 클라이언트 등의 경계에 사용한다. 내부 협력 모듈도
호출부와의 안정된 계약을 통해 대체할 수 있다. 내부 함수의 호출 순서와 구현
세부사항을 고정하기 위한 mock은 피한다. 테스트를 위해 제품의 공개 API를 넓히지 않는다.

DB double의 호출 검사는 실제 SQL의 잠금·원자성·rollback을 증명하지 않는다.
fixture에서 주입한 Action과 router의 결과는 실제 Next transport와 RSC 상태 보존을
증명하지 않는다. fake client나 다른 OS에서의 통과도 해당 native 환경의 통과로
보고하지 않는다. 대체한 범위와 실제 실행한 환경을 결과에 구분한다.

### 4. 중요한 거부에는 부작용이 없는지도 확인한다

- 변경과 관련된 다른 사용자·프로젝트의 접근, 토큰 scope, 플랜 상한, stale version,
  잘못된 상태 전이를 선택한다. 정상 대조군과 거부 사례가 권한·입력 등의 차이 때문에
  서로 다른 결과를 내는지 확인한다.
- 거부 결과와 함께 프로젝트 상태·이벤트·토큰 등에 금지된 변경이 없는지 확인한다.
  계약상 필요한 감사 기록과 요청 제한 집계는 해당 계약의 예상 결과로 검사한다.
- 저장·경합 변경은 성공·충돌 결과와 최종 DB 상태를 함께 검사한다. 실패가 일부
  저장을 남기지 않는지도 확인한다.
- 비동기 복구 변경은 pending 중 중복 제출, 이전 프로젝트나 요청의 늦은 응답,
  저장 전·후의 응답 유실 중 관련된 사례를 포함한다. 복구 과정의 추가 mutation과
  최종 저장 상태를 확인해 중복 실행이나 최신 상태의 덮어쓰기를 검출한다.

### 5. 독립적으로 재현 가능하게 만든다

- 단독 실행과 전체 suite에서 같은 계약을 검증한다. 다른 테스트의 실행 순서나
  남긴 데이터에 의존하지 않으며, 데이터·세션·임시 경로·사용 자원을 격리한다.
- 시간과 응답 순서를 제어한다. 시계·제어 가능한 Promise·checkpoint·상태를 기다리는
  assertion을 사용하며, 성공을 기대하는 고정 `sleep`으로 경합을 맞추지 않는다.
  기다리는 작업에는 실패를 판별할 수 있는 제한 시간을 둔다.
- 실제 경합은 분리된 연결이나 작업과 명시적인 동기화 지점으로 재현한다. 제품의
  잠금과 transaction은 실행하고, 테스트가 통과하도록 저장 결과를 대체하지 않는다.
- 실패해도 `finally`나 테스트 종료 hook에서 자신이 만든 fixture·연결·서버·자식
  프로세스를 정리한다. 테스트가 소유하지 않은 데이터와 프로세스는 보존한다.
  임시 경로와 DB 분리는 기존 배치 규칙과 안전 실행 절차를 따른다.

### 6. 실제 실행과 증거를 확인한다

- 새로 추가하거나 이동한 파일이 해당 실행 명령의 검색 패턴에 포함되고, 결과에
  나타나는지 확인한다. 새 확장자나 경로에 필요한 실행 환경도 같은 변경에서 맞춘다.
- TypeScript 테스트의 타입 검사를 유지한다. 타입 검사 전용 사례는 실행 테스트와
  구분하고 담당 명령을 명시한다. 런타임 API는 로컬 설치뿐 아니라 해당 CI의 Node와
  실행 환경에서 지원되는지 확인한다.
- CI에 집중 실행 설정을 남기지 않는다. skip에는 환경 조건과 이유를 남기고,
  필수 검증 환경이 준비되지 않았으면 미실행 또는 차단으로 보고한다. 재시도만으로
  반복 실패를 숨기지 않는다.
- 결과에는 검증 대상, 실제 실행 명령, 통과·실패·skip·미실행, double 사용 범위와
  남은 확인 사항을 기록한다. fresh build가 필요한 검사는 해당 build 뒤에 실행한다.
  개별 명령의 통과를 전체 workflow나 운영·배포·다른 OS의 통과로 확대하지 않는다.
- 저장소에 별도 인수·회귀 보고서를 남길 때는 [검증 보고서 규칙](../test-reports/README.md)을
  따른다. 모든 작은 변경에 새 보고서 파일을 만들 필요는 없으며, PR이나 작업 결과에
  위 실행 근거를 남길 수 있다.

## 권장 작성 관례

- 테스트 이름은 조건·행동·기대 결과가 드러나게 쓴다.
  예: `이전 버전으로 저장하면 stale을 반환하고 파이프라인을 변경하지 않는다`.
- AAA 흐름을 코드 순서와 빈 줄로 표현한다. 설명용 주석이나 시험 나레이션은
  [코드 주석 규칙](../../AGENTS.md#code-comments)을 따른다.
- 한 테스트는 하나의 동작이나 응집된 계약에 집중한다. 그 계약을 증명하는 데 필요한
  assertion은 여러 개여도 된다. 같은 계약의 조건별 사례는 읽기 쉬운 표로 묶을 수 있다.
- 작은 fixture와 명시적인 입력을 사용한다. 공유 factory를 쓰더라도 결과를 결정하는
  중요한 값과 차이는 테스트 본문에서 확인할 수 있게 한다.
- DOM 요소는 역할과 접근 가능한 이름·label로 찾는 것을 우선한다. 실제 사용자의
  조작과 관찰 결과를 연결하고, 브라우저 고유 동작에는 실제 입력을 사용한다.

## 리뷰 확인

- 보호하는 계약과 그 계약을 깨는 실패 사례가 분명한가?
- 동작을 보존하는 내부 리팩터링에도 테스트가 유지되는가? 구조 자체가 계약이면
  그 비교가 필요한 이유와 범위가 분명한가?
- 관련 거부·경합·복구에서 반환 결과와 허용되거나 금지된 부수효과를 확인했는가?
- 독립 실행·정리·검색·타입 검사·CI 환경과 실제 실행 근거를 확인했는가?

기존 `node:test`·서버 bootstrap·격리 PostgreSQL·리허설을 활용해 새로 작성하거나
수정하는 사례부터 적용한다. 새 runner·CI·커버리지 게이트는 검증 누락, 반복 비용,
실행 시간과 불안정성을 근거로 별도 판단한다. 기존 사례의 이동·통합·삭제는 배치와
실행 계약을 함께 검토하며, 작성 규칙만으로 일괄 개편하지 않는다.
