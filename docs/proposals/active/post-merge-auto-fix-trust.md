# 실패 자동 수정을 믿을 수 있게 만든다

## Summary

병합 후 검사의 실패를 에이전트가 고쳐 PR로 올리는 장치(`post-merge-auto-fix.md`)를
만들면서, 에이전트가 낸 수정과 메모를 믿을 근거가 없다는 것이 드러났다. 이 문서는 그
문제가 어디서 생기는지를 적고, 믿는 대신 확인하는 범위를 넓혀 해결하는 방법을 제안한다.
핵심은 실패를 재현하는 일을 에이전트에게서 워크플로로 옮기는 것이다. 워크플로가 먼저
재현하고, 재현된 실패에만 에이전트를 부르고, 같은 방법으로 수정을 잰다. 이 변경은
자동 실행을 위한 준비가 아니다. 사람이 손으로 워크플로를 실행할 때도 필요하다. 이
저장소의 주인은 코드를 줄마다 읽지 않고 장치가 내놓는 증거로 판단하므로, 측정을
믿을 수 없으면 누가 불렀든 결과를 믿을 수 없다. 저절로 불리게 하는 것(자동 실행)은
이 변경 뒤의 별개의 일이고, 숫자로 정한 켜는 기준이 채워진 뒤로 미룬다.

## Goal

- 수정을 PR로 올릴지 말지의 판정이 에이전트가 정한 것에 기대지 않게 한다.
- 워크플로가 재현하지 못한 실패에는 에이전트를 부르지 않는다.
- 자동 실행을 켜는 기준을 숫자로 미리 정한다.
- 작업 유형: 기존 워크플로와 스크립트의 변경, 잡 하나의 추가.

## Proposal Size

`proposal-size`: standard

선택 근거:

- 워크플로의 잡 구성과 판정 규칙을 바꾸고, 5개 이상의 파일을 고친다.
- 실제 모델을 쓰는 연습 실행과 러너에서의 실험이 필요하다.

## Current State

파일 두 곳에 냈다. 측정은 고치기 전과 고친 뒤 모두 40번 중 0번 실패였는데, 시험이 돌지
않은 결과였다. 이 시험들은 `STAGEKEEPER_TEST_WINDOWS_RUNTIME`이 없으면 건너뛴다. 원래
검사는 시험 단계에서 그 값을 넣고, 수정 워크플로의 수정 잡과 측정 잡은 넣지 않는다.

여기서 세 가지가 드러났다.

- 원인은 매번 맞게 짚었다. 금지한 것(단언 삭제, 시간 한도 변경, 금지 경로, 네트워크
  조회)은 한 번도 어기지 않았다.
- 스스로 한 말은 틀릴 때가 있다. "빌드가 빨라졌다"와 "이 러너는 Intel이 아니다"가
  사실이 아니었다.
- 재현하려는 정도가 지시문의 문장 하나에 따라 31초에서 15분까지 달라진다. 오래
  되풀이하라는 요구를 빼자 재현하려는 노력 자체가 사라졌고, 실패가 나는 명령을 찾으라고
  하자 재현은 했지만 다른 러너에서 돌 수 없는 명령을 냈다. 지시문을 세 번 고쳤고 세 번
  다 다른 곳이 어긋났다.

### 에이전트가 내는 것과 지금 믿는 정도

| 내는 것 | 지금의 처리 | 믿나 |
| --- | --- | --- |
| 메모 | 이슈의 코드 블록에 "지시가 아닌 기록"으로 적는다. 판정에 쓰지 않는다 | 믿지 않는다 |
| 고친 코드 | 금지 경로를 워크플로가 다시 보고, 지문으로 견주고, 원래 검사를 부르고, 측정 잡이 전과 후를 잰다 | 믿지 않고 확인한다 |
| 재현 명령 | 측정 잡이 그 명령을 그대로 되풀이한다 | 믿는다 |

세 번째가 구멍이다. 측정 잡은 직접 돌려서 세지만 무엇을 돌릴지는 에이전트가 정한다.

- 실패가 나지 않는 명령을 내면 측정은 아무것도 가려내지 못한다(연습 1: 39번 중 0번).
- 측정 잡에서 돌 수 없는 명령을 내면 시험과 무관하게 늘 실패한다. 측정 잡은 그것을
  실패로 센다(연습 1 재실행: 16번 중 16번).
- 실제 실패와 무관하게 "고치기 전에는 실패하고 고친 뒤에는 통과하는" 명령을 내면
  측정은 "확인됨"이 된다.

이 구멍을 막는 것으로 `post-merge-auto-fix.md`가 든 것은 전체 검사와 사람의 리뷰다.
그런데 이 저장소의 주인은 PR을 요약으로 보겠다고 했다. 사람의 리뷰에 기대는 부분이
실제로는 약하다.

### 다른 곳은 어떻게 하나

조사는 Sonnet 서브에이전트가 했고 원문을 직접 대조하지는 않았다. 출처가 확인됐다고
보고된 것만 적는다.

| 방법 | 쓰는 곳 | 내용 |
| --- | --- | --- |
| 시스템이 먼저 재현하고, 안 되면 멈춘다 | Uber FlakyGuard (https://arxiv.org/html/2511.14002v1) | 수정을 만들기 전에 시험을 기본 1000번 돌린다. 재현하지 못하면 멈춘다. 고친 시험은 같은 횟수를 모두 통과해야 한다. 1115개 중 798개를 재현했고, 380개의 수정을 냈고, 개발자가 197개(51.8%)를 받아들였다 |
| 실패의 지문으로 같은 실패를 묶는다 | Chromium LUCI Analysis (https://pkg.go.dev/go.chromium.org/luci/analysis/internal/clustering/algorithms/failurereason) | 실패 문구에서 주소, 임시 파일 이름, 숫자를 지운 것으로 묶는다 |
| 통과하지 못한 수정은 보여 주지 않는다 | GitHub Copilot Autofix, Google의 빌드 수정 | 기계 검사를 통과한 것만 사람에게 보인다 |
| 숫자로 정한 한도 안에서만 자동화한다 | Google SafeRevert (https://hackthology.com/saferevert-when-can-breaking-changes-be-automatically-reverted.html) | 잘못된 되돌리기 1% 미만, 하루 5건 이하를 먼저 정하고 그 선을 지키는 경우만 자동으로 되돌린다 |
| 보이는 시험만으로는 부족하다 | SWE-bench 과적합 연구 (https://arxiv.org/abs/2511.16858) | 에이전트가 볼 수 있는 시험은 통과하지만 숨겨 둔 시험에서 틀리는 패치가 22~36%였다 |
| 다른 모델의 검토는 승인 도구가 못 된다 | Google의 판정 모델 연구 (arXiv 2511.10865) | "맞다"고 한 것 가운데 실제로 맞은 것이 65%였다 |

가끔 실패하는 시험에 잡음을 넣어 재현하는 연구(Shaker,
https://cin.ufpe.br/~damorim/publications/Silva_ETAL_ICSME20.pdf)는 도움이 된다고
보고했고, 다른 언어에서의 재현 연구는 차이가 없다고 보고했다. 잡음을 넣으면 반드시
재현된다고 볼 수 없다.

### 이 저장소에서 잰 재현율

같은 시험 파일(`plugin/bin/harness-watch.test.mjs`, 커밋 `c5f4e44`, macOS Intel)을
방법만 바꿔 잰 결과다.

| 방법 | 실패 | 출처 |
| --- | --- | --- |
| 부하 없이 파일 하나 | 39번 중 0번 | 연습 1의 측정 잡 |

방법에 따라 0%에서 11%까지 벌어진다. 어느 방법을 쓸지가 이 제안의 중심이다.

### 실패 로그에 있는 것

실패한 잡의 로그에는 워크플로가 스스로 재현하는 데 필요한 것이 들어 있다.

```text
not ok 339 - honors a longer Retry-After, and a healthy overview restarts failure counting
  location: '/Users/runner/work/stagekeeper/stagekeeper/plugin/bin/harness-watch.test.mjs:432:1'
  error: |-
    Expected values to be strictly equal:
    'idle' !== 'work'
```

시험의 이름, 파일과 줄, 오류 문구다. 시험 실행기가 내는 형식이라 이름으로 저장소를
뒤질 필요가 없다.

## Scope

포함 범위:

- 수정 워크플로에 재현 잡을 더하고, 측정 계획을 에이전트가 아니라 워크플로가 정하게
  한다.
- 재현된 실패가 원래의 실패인지를 지문으로 대조한다.
- 부하를 주는 방법을 러너에서 재 보고 정한다.
- 자동 실행을 켜는 기준과 켠 뒤의 한도를 숫자로 정한다.

제외 범위:

- 시험 이름이 없는 실패(빌드 시간 초과, 설치 실패 등)를 자동으로 고치는 일. 워크플로가
  재현할 수 없으므로 사람에게 넘긴다.
- 자동 실행 자체의 구현(`post-merge-auto-fix.md`의 4-가, 4-나). 이 제안이 끝난 뒤에
  다시 정한다.
- 다른 모델에게 수정을 검토시키는 일.
- 에이전트의 셸을 가두는 일. `post-merge-auto-fix.md` 8절에 쓸 수 없는 이유를 적었다.

## Proposal

### 1. 재현을 워크플로가 갖는다

지금의 순서는 "에이전트가 고친다 → 에이전트가 낸 명령으로 잰다"이다. 다음으로 바꾼다.

| 순서 | 잡 | 하는 일 | 모델 |
| --- | --- | --- | --- |
| 1 | 재현 | 실패 로그에서 실패한 시험을 뽑고, 그 시험 파일을 정해진 부하 아래에서 되풀이한다 | 안 쓴다 |
| 2 | 수정 | 재현된 실패에 대해서만 에이전트를 부른다. 에이전트는 고친 코드와 메모를 낸다 | 쓴다 |
| 3 | 측정 | 재현 잡이 쓴 것과 같은 명령으로 고치기 전과 고친 뒤를 번갈아 잰다 | 안 쓴다 |

- 측정 계획(명령과 횟수)은 재현 잡이 만들어 지문과 함께 잡의 출력으로 낸다.
  에이전트가 낸 측정 계획은 읽지 않는다.
- 재현 잡이 정해진 횟수 안에 실패를 보지 못하면 에이전트를 부르지 않는다. 시도로
  세지 않고 "재현 안 됨"으로 기록한다. 모델 사용량이 들지 않는다.
- 에이전트에게는 재현 잡이 쓴 명령과 그 결과를 알려 준다. 에이전트가 그 명령을
  바꿀 길은 없다.
- 재현 잡과 측정 잡은 실패한 잡과 같은 종류의 러너에서 돈다. 지금의 측정 잡과 같다.
- 재현 잡과 측정 잡은 실패한 단계가 받던 환경 변수를 그대로 받는다. 단계의 환경은
  워크플로 파일에 적혀 있으므로, 워크플로마다 필요한 값을 수정 워크플로의 스크립트가
  갖고 시험이 그 값을 원래 워크플로의 단계와 대조한다.
- 대상 시험이 건너뛰어진 실행은 통과로 세지 않고 "돌지 않음"으로 센다. 돌지 않은
  실행뿐이면 재현 잡은 "다루지 않는 실패"로 끝낸다.

이렇게 하면 에이전트가 정하는 것이 고친 코드 하나로 줄어든다. 지금의 지시문에서
재현에 관한 부분(실패가 나는 명령을 찾아라, 부하를 만들어라)을 뺀다. 재현하려는
정도가 지시문의 문장에 따라 흔들리는 문제가 함께 사라진다.

### 2. 실패의 지문

재현 잡은 실패 로그에서 다음을 뽑는다.

| 뽑는 것 | 쓰는 곳 |
| --- | --- |
| 실패한 시험의 파일 | 되풀이할 대상 |
| 실패한 시험의 이름 | 재현된 실패가 같은 시험인지 |
| 오류 문구에서 숫자, 경로, 주소, 시각을 지운 것 | 같은 이유로 실패했는지 |

- 한 이슈의 로그 여러 건에서 뽑은 것을 모은다. 이슈는 단계 단위라 서로 다른 시험이
  실패한 로그가 모인다.
- 재현 실행에서 실패한 시험의 이름이 모은 이름 가운데 하나와 같을 때만 "재현됨"으로
  센다. 다른 시험만 실패했으면 세지 않고 따로 적는다.
- 오류 문구의 대조는 처음에는 기록만 하고 판정에 쓰지 않는다. 같은 시험이 다른
  문구로 실패하는 경우가 얼마나 되는지 모른다.
- 로그에서 파일을 뽑지 못하면(시험 실행기의 출력이 아닌 실패) 재현 잡은 "다루지
  않는 실패"로 끝낸다.

파일 경로는 저장소 안의 추적되는 파일이고 이름이 `.test.`를 가진 것만 받는다.
로그는 외부 패키지의 출력이 섞일 수 있는 글이므로, 뽑은 경로를 그대로 명령에 넣지
않고 저장소의 파일 목록과 대조한다.

### 3. 부하를 주는 방법은 재 보고 정한다

"Current State"의 표처럼 방법에 따라 재현율이 크게 다르다. 워크플로에 박아 넣기 전에
잰다.

- 대상: 지난 실패 두 건(`harness-watch`의 커밋 `c5f4e44`, Windows의 임시 파일 삭제
  실패의 커밋 `669349a`)과, 가끔 실패한 적이 없는 시험 파일 하나(거짓 재현이 나는지
  본다).
- 견줄 방법: 부하 없음, 같은 파일을 N개 동시에(N은 2, 4, 8), CPU를 쓰는 프로세스를
  K개 띄우고 파일 하나(K는 러너의 코어 수와 그 두 배), 둘을 함께.
- 재는 것: 방법마다 40분 안에 돌린 횟수, 실패 수, 실패한 시험의 이름.
- 고르는 기준: 지난 실패를 가장 자주 재현하면서, 실패한 적 없는 시험은 실패시키지
  않는 방법. 여럿이면 가장 단순한 것.

부하는 워크플로의 스크립트가 만든다. 어느 운영체제에서나 되는 방법(Node 프로세스로
CPU를 쓰는 것, 같은 파일을 동시에 돌리는 것)만 쓴다. Linux 전용 도구(stress-ng,
cgroups)는 쓰지 않는다. macOS와 Windows 러너에서 도는지 확인되지 않았다.

실험은 모델을 쓰지 않는다. `harness/auto-fix-agent-trial` 브랜치에서 쓴 측정
워크플로와 같은 방식으로 돌린다.

### 4. 판정

| 재현 잡 | 측정 잡 | 판정 |
| --- | --- | --- |
| 재현됨 | 고친 뒤 실패 0, 필요한 횟수를 채움 | PR을 연다 |
| 재현됨 | 고친 뒤 실패 0, 횟수가 모자람 | PR을 열고 `auto-fix:under-verified`를 붙인다 |
| 재현됨 | 고친 뒤에도 원래의 시험이 실패 | 열지 않는다 |
| 재현됨 | 고친 뒤 원래의 시험은 통과, 다른 시험이 실패 | 열지 않는다. 다른 시험의 이름을 적는다 |
| 재현 안 됨 | 돌지 않는다 | 에이전트를 부르지 않는다 |
| 다루지 않는 실패 | 돌지 않는다 | 에이전트를 부르지 않는다. 사람에게 넘긴다 |

- 필요한 횟수는 지금과 같이 `3 × 돌린 횟수 ÷ 실패 수`다. 실패율이 p일 때 n번 연속
  통과할 확률이 `(1-p)^n`이고, 5% 수준으로 "실패율이 p 이상"을 기각하려면 약 `3/p`번이
  필요하다는 계산과 같다.
- `auto-fix:not-reproduced` 경로는 없어진다. 재현하지 못한 실패에는 에이전트를 부르지
  않으므로 "재현하지 못한 채 시험 파일만 고친 PR"이 생기지 않는다.
- 사람이 손으로 실행할 때는 재현을 건너뛰는 입력을 둔다. 사람이 원인을 알고 있고
  수정의 초안만 받고 싶은 경우다. 그 PR에는 재현하지 않았다는 표시가 붙고, 자동
  실행은 이 입력을 쓰지 못한다.

### 5. 이 방법이 다루지 못하는 것

- 시험 이름이 없는 실패. 지난 실패 세 건 가운데 오프라인 빌드의 시간 초과가 그렇다.
- 드문 실패. 시험 파일 하나가 1분쯤 걸려 40분에 40번쯤 돈다. 그 횟수로 고쳐졌다고 할
  수 있는 것은 실패율이 7%쯤 이상인 실패다. 더 드문 실패는 재현부터 되지 않는다.
- 기한만 늘려 실패를 가린 수정. 조사한 연구에도 이것을 가려내는 검사가 없었다. 단언의
  삭제와 건너뛰기 표시는 지금도 세어 PR에 적지만, 기한을 늘린 것이 옳은 수정인지는
  사람이 봐야 한다.
- 수정이 원인을 고쳤는지. 재현율이 0이 됐다는 것까지만 말할 수 있다.

### 6. 자동 실행을 켜는 기준

이 절은 1절부터 5절까지와 따로다. 1절부터 5절은 손으로 실행할 때도 필요하고, 이 절은
자동 실행을 켤 때만 필요하다. 1절부터 5절의 승인과 구현은 이 절의 숫자를 기다리지
않는다.

지금까지는 "실제 실패를 몇 건 써 본 뒤 정한다"였고 기준이 없었다. 숫자는 자동 실행을
다시 정할 때 주인이 정한다. 아래는 시작값이다.

| 정할 것 | 시작값 |
| --- | --- |
| 손으로 돌려 볼 실제 실패의 수 | 5건 |
| 켜는 조건 | 5건 가운데 4건 이상에서 PR이 병합되고, 병합 뒤 `3 × 실패 한 번당 실행 횟수`만큼 그 검사가 통과함 |
| 자동으로 여는 범위 | 재현됨이고, 측정을 통과했고, 시험 파일만 고친 변경 |
| 켠 뒤의 한도 | 자동으로 연 PR이 병합된 뒤 같은 이슈가 다시 열린 것이 2건이면 자동 실행을 멈춘다 |

- 제품 코드를 고친 변경은 자동 실행에서도 PR을 열되, 켜는 조건의 셈에 넣지 않고 주인이
  직접 본다는 표시를 붙인다.
- 한도에 닿아 멈춘 것은 `post-merge-auto-fix.md` 6절의 전용 이슈로 알린다.

### 7. 택하지 않은 방법

| 방법 | 택하지 않은 이유 |
| --- | --- |
| 지시문으로 재현을 요구하기 | 지시문의 문장에 따라 재현하려는 정도가 31초에서 13분까지 달라졌다. 오래 되풀이하라는 요구는 두 번 다 지켜지지 않았다 |
| 다른 모델에게 수정을 검토시키기 | 판정 모델의 정밀도가 65%로 보고됐다. 검토의 결과도 믿을 수 없는 글이다. 사용량이 두 배로 든다 |
| 측정 잡이 실패한 단계의 원래 명령을 돌리기 | `harness-watch` 건의 단계 명령은 한 번에 7분이다. 필요한 횟수를 채우지 못한다 |
| 재현 명령의 이름만 대조하고 명령은 에이전트에게 맡기기 | 실패가 나지 않는 명령을 내는 문제가 남는다. 명령을 워크플로가 가지면 대조도 함께 된다 |
| Uber처럼 1000번 돌리기 | 40분에 40번쯤이다. 드문 실패는 다루지 않는 것으로 한계를 적는다 |
| 에이전트의 셸을 가두기 | 이 제품이 macOS의 샌드박스와 launchd를 직접 쓴다. 가둔 셸에서는 그 시험이 돌지 않는다 |

### 8. 멈춘 지점과 이어 가는 방법

2026-11-24에 여기서 멈췄다. 급한 기능 작업이 먼저이고, 확인 한 번에 30분에서 한 시간이
걸리는 일이라 이어서 하지 않았다.

지금 있는 것:

| 것 | 어디에 | 상태 |
| --- | --- | --- |
| 실패 이슈의 상태 줄, 라벨, 자동으로 닫기 | `main` | 쓰고 있다 |
| 에이전트를 뺀 수정 워크플로(측정, 브랜치, 전체 검사, PR, 기록) | `main` | 손으로 실행한다 |
| 결과물을 믿지 않게 한 보완, 에이전트 잡 | `dev`(PR #437, #439) | 손으로 실행한다. `main`에는 다음 승격 때 올라간다. 그 전에는 실행할 때 `--ref dev`를 준다 |
| 저절로 불리는 부분(`post-merge-auto-fix.md`의 4-가, 4-나) | 없음 | 보류 |
| 연습용 이슈 | #430 | 시도 기록이 댓글로 있다 |
| 실험 브랜치 `harness/auto-fix-agent-trial` | 원격에만 | 병합하지 않는다. 측정 워크플로(`auto-fix-agent-trial-measure.yml`), 부하 스크립트(`stress.mjs`), 셸 명령이 무엇을 볼 수 있는지 재는 워크플로(`auto-fix-credential-probe.yml`)가 있다. 3절의 실험에서 다시 쓴다 |
| 저장소 설정 "Allow GitHub Actions to create and approve pull requests" | 켜짐 | 수정 워크플로가 PR을 열 때 필요하다 |

이어 갈 때의 순서는 Execution Plan이다. 첫 일은 3절의 실험이고 모델을 쓰지 않는다.
1절부터 5절까지가 다음에 할 일이다. 자동 실행을 하지 않더라도 한다.

이 문서가 끝난 뒤 자동 실행(self recovery)까지 남는 일은 세 덩어리다.

| 덩어리 | 내용 | 크기 |
| --- | --- | --- |
| 저절로 실행시키는 부분 | `post-merge-auto-fix.md`의 4-가와 4-나. 실행시킬지의 판정, 한 이슈에 수정 하나, 두 번째 시도, 사람에게 넘기기, 한도와 비밀 값에서 멈추기, 스위치, 수정 뒤 지켜보기. 그 문서의 설계는 이 문서 이전의 모습이라 먼저 고쳐 써서 다시 승인받는다. 실패 기록이 최근 72시간만 읽는 것, 16절의 상태 표가 코드와 어긋난 것, 계획 잡이 실패하면 기록이 남지 않는 것도 여기서 푼다 | 수정 워크플로와 비슷하다 |
| 켜도 되는지의 숫자 | 6절의 기준을 정하고, 실제 실패를 손으로 돌려 센다. 실패가 나야 셀 수 있다. 2026-11-20 이후 병합 후 실패가 없어서 기다려야 한다 | 일이 아니라 시간이다 |
| 켜기 전에 갖출 것 | `dev`에 검사가 통과해야 병합되는 규칙을 건다(지금은 PR로만 바뀐다는 규칙만 있다). CI 전용 모델 토큰을 쓸지 정한다. Claude Code의 판을 고정할지 정한다(실행마다 최신판을 설치하고, 판에 따라 권한 방식이 달라지는 것을 봤다). 미리 만든 변경으로 세 러너에서 다시 돌려 워크플로가 그사이 깨지지 않았는지 본다(평소의 검사는 이 워크플로를 돌리지 않는다). `workflow_dispatch`의 입력 개수 한도(지금 10개를 쓴다)와, 구독 한도에 걸렸을 때의 출력을 확인한다 | 다 합쳐 반나절이 안 된다 |

이것을 다 하면 켜도 되는지를 판단할 수 있게 된다. 켜도 되는지는 그때 센 숫자가
정한다. 기준을 채우지 못하면 다 만들어 놓고도 켜지 않는다. 지금까지 에이전트의 수정이
통했다고 따로 잰 값으로 확인된 것은 17절의 실험에서 한 번이다.

단계마다 시작할 때 몰랐던 것이 두세 개씩 나왔다(로그를 받는 명령, 묶음 파일의 문법,
결과물과 캐시, 가두면 제품의 시험이 돌지 않는 것, 다른 러너에서 돌지 않는 명령,
건너뛰어진 시험). 남은 일도 그럴 것으로 본다.

켜진 뒤에도 병합은 사람이 하고, 워크플로가 연 PR의 `check`는 사람이 승인해야 돈다.
저절로 고치는 것은 이름이 있는 시험의 실패뿐이다(5절).

자동 실행을 다시 꺼내 볼 기준: 병합 후 실패가 한 달에 세 건을 넘는다.

하지 않기로 한 것:

- 재현을 지시문으로 고치는 일. 지시문을 세 번 고쳤고 세 번 다 다른 곳이 어긋났다.
- 이 문서의 1절부터 5절이 끝나기 전에 자동 실행을 만드는 일.

에이전트 잡을 손으로 쓰는 방법(실제 실패가 났을 때):

```bash
gh workflow run post-merge-auto-fix.yml --ref dev \
  -f issue=<이슈 번호> -f runner=<실패한 잡의 러너> -f workflow=<부를 검사 또는 none> \
  -f source=agent -f model=claude-sonnet-5-5 \
  -f runs=<실패한 실행 번호들> -f job=<실패한 잡의 이름> -f open_pr=true
```

나온 PR의 측정 숫자는 에이전트가 정한 명령의 결과다. 이슈에 적힌 명령이 실제 실패를
재는지 보고, 시험이 건너뛰어지지 않았는지 본다. 이 문서가 끝나기 전에는 측정을 근거로
병합하지 않는다.

## Safety Analysis

- 재현 잡은 모델을 쓰지 않고 에이전트의 코드도 돌리지 않는다. 돌리는 것은 `dev`에
  있는 시험 파일이다.
- 로그에서 뽑은 경로는 저장소의 추적되는 시험 파일과 대조한 뒤에만 쓴다. 로그의
  글을 명령으로 넣지 않는다.
- 에이전트가 정할 수 있는 것이 줄어든다. 지금보다 넓어지는 권한이 없다.
- 부하를 만드는 프로세스는 측정이 끝나면 워크플로의 스크립트가 끝낸다. 러너는
  잡이 끝나면 사라진다.

## Risks and Rollback

잔여 리스크:

- 부하를 주는 방법이 지난 실패 두 건에는 맞고 다음 실패에는 맞지 않을 수 있다. 재현
  하지 못한 실패는 사람에게 넘어가므로 틀린 PR이 열리지는 않는다. 자동으로 다루는
  실패가 줄 뿐이다.
- 부하가 실패한 적 없는 시험까지 실패시키면 거짓 재현이 난다. 이름을 대조하므로 원래
  실패한 시험이 아니면 세지 않는다. 같은 시험이 부하 때문에만 실패하는 경우는
  가려내지 못한다.
- 5절의 한계는 남는다.
- 에이전트가 모델 토큰을 읽어 내보내는 길은 이 변경으로 줄지 않는다.
  `post-merge-auto-fix.md` 8절의 한계 그대로다.

롤백 방법:

- 워크플로와 스크립트의 변경을 되돌린다. 손으로 실행할 때만 도는 워크플로라 되돌리는
  동안 영향받는 것이 없다.
