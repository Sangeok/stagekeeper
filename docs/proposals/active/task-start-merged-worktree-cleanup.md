# 다음 작업을 시작할 때 사람이 병합한 작업 트리 정리하기

## Summary

사람이 GitHub 웹에서 PR을 만들고 병합한다. 에이전트는 작업 트리 사용을 마치면 `npm run task -- release`로 그 사실을 기록한다. 같은 로컬 저장소에서 다음에 `npm run task -- start`를 실행하면, 이전에 인계한 작업이 `dev`에 병합됐는지 확인하고 정리할 수 있는 작업 트리와 로컬 브랜치만 제거한다. 다음 작업까지의 지연을 허용하므로 PC별 스케줄러나 주기적인 모델 호출이 필요 없다.

## Goal

작업자는 새 브랜치와 작업 트리를 만들 때 명령 이름으로 그 용도를 알 수 있어야 한다. PR을 만들거나 병합하는 시점은 사람이 정하고, 로컬 사용 종료와 병합이 모두 확인된 작업을 따로 기억해서 치우는 부담을 줄인다.

## Proposal Size

`standard`. 새 CLI 계약을 만들고 이전 세션이 남긴 파일과 브랜치를 삭제할 수 있는 시점을 바꾼다. 설계 위험도는 HIGH-RISK다. 승인 판단의 핵심은 **특정 작업에 대해 소유자가 남긴 사용 종료 기록을 나중 세션이 어디까지 사용할 수 있는가**다.

## Scope

개발용 CLI, 로컬 Git 작업 원장, GitHub 조회, 기존 정리 검사와 저장소 작업 지침이 대상이다. 자동 제거의 적용 단위는 같은 PC·같은 OS 계정이 사용하는 로컬 복제본과 관리 도구 설치다. 여러 계정이나 호스트가 작업 트리를 함께 사용하는 환경은 현재 프로세스 관측 범위를 벗어나므로 보존한다. 서버·플러그인 배포, GitHub 병합 자동화, 원격 브랜치 삭제, 상주 서비스, Windows 자동 삭제 자격 확대는 범위 밖이다.

## Proposal

### 작업자가 보게 될 흐름

| 시점 | 동작 | 결과 |
| --- | --- | --- |
| 새 독립 작업 시작 | 에이전트가 기존 생성 인자 `--owner`, `--branch`, `--path`로 `npm run task -- start`를 호출한다. | 정리 대상으로 인계된 작업을 확인한 뒤 새 작업 ID, 인스턴스, 상태 OID와 경로를 돌려준다. |
| 이번 작업 인계 | 소유자가 터미널·서버·공유 사용을 끝내고 대상 밖 관리용 체크아웃에서 `npm run task -- release`를 호출한다. | 로컬 인계만 기록한다. PR 번호는 선택 사항이며 아직 PR이 없어도 된다. |
| 미병합 PR의 리뷰 수정 | 소유자가 작업 트리를 다시 사용하기 **전에** 관리용 체크아웃에서 `npm run pr -- resume --task <id> --owner <owner> --expected-state <oid>`의 성공을 확인한다. | 같은 HEAD에서도 인계가 취소된다. 수정이 끝나면 새 상태로 다시 인계한다. 경합에서 이미 병합이 확인된 작업은 후속 작업용으로 재사용하지 않는다. |
| GitHub에서 PR 생성·병합 | 사람이 원하는 시점에 같은 저장소의 브랜치에서 `dev` 대상으로 진행한다. | 이 시점에는 로컬 명령을 실행할 필요가 없다. |
| 이후의 작업 시작 | 다음 `task start`가 아직 유효한 인계만 확인한다. | 새 작업의 생성 결과와 별도로 이전 PR 번호, 작업 트리·로컬 브랜치 각각의 결과, 보존한 경로와 사유를 출력한다. |

예를 들어 월요일에 PR 없이 인계하고 화요일에 웹에서 PR을 만들어 병합했다면, 수요일의 첫 `task start`가 정리를 시도한다. 화요일에 리뷰 수정을 위해 인계를 취소했다면 수요일에는 그 작업을 건너뛴다.

### REQ-TSC-001 — 새 작업 시작과 명령 호환

새 작업 요청이 유효하면 `task start`는 기존 `create`와 같은 생성 검증을 거쳐 새 작업을 한 번 등록해야 한다. 전환 기간의 `pr create`는 기존 인자, 출력, 종료 코드와 생성 전용 동작을 유지한다. `status`와 `inspect`는 계속 읽기 전용이다.

`task`의 공개 동사는 `start`, `release` 두 개로 제한한다. 예를 들어 `npm run task -- complete`는 인자 검사에서 거절한다. 두 npm 진입점은 기존 `scripts/pr/`의 파서·관리 소스 검증·작업 생성 로직을 공유한다. 아래 두 명령은 제안하는 공개 호출 형식이다.

~~~sh
npm run task -- start --owner <owner> --branch harness/<topic> --path <absolute-new-path>
npm run task -- release --task <id> --owner <owner> --expected-state <oid> --expected-head <sha> --expected-instance <uuid> --request-id <uuid> --usage-ended
~~~

두 호출은 기존 `--root <control>`을 지원한다. `release`에는 `--pr <number>`를 선택적으로 붙인다. `start` 호출이 중단된 뒤 생성 의도가 이미 기록됐다면 `pr status`에서 대상 branch·path와 task를 확인한다. `creating`이면 기존 `pr create --task …`로 생성만 복구하고 `working`이면 기록된 생성 결과를 사용한다. 응답 유실 자체는 새 task 등록 사유가 될 수 없다.

### REQ-TSC-002 — 사용 종료를 기록하고 취소하는 시점

소유자가 실제 사용을 마치고 `release`를 호출하면 도구는 등록된 작업 ID, owner, 예상 상태 OID, 인스턴스, 마지막 HEAD, 요청 ID와 사용 종료 선언을 확인해야 한다. 소유자의 선언은 **그 작업이 해당 HEAD로 병합된 뒤 기존 제거 검사를 통과할 때 한 번 정리할 권한**을 부여한다. 기존 인계 검사로 파일 지문을 기록하며, 대상 경로 안에서 사용 중이거나 식별이 틀리면 인계가 성립하지 않는다. 동일 요청을 다시 받으면 중복으로 등록하지 않는다. 번호를 생략하면 오프라인에서도 로컬 인계가 가능하다. 번호를 제공하면 GitHub에서 읽어 검증한 PR만 연결하며, 불일치나 조회 실패는 인계 상태를 쓰기 전에 보고한다.

리뷰를 재개하면 현재 인계를 취소해야 한다. HEAD나 지문이 달라졌거나 경로가 재사용됐으면 예전 기록으로 정리할 수 없다. 소유자 이름만 같거나 PR이 오래됐다는 사실은 인계의 근거가 되지 않는다.

### REQ-TSC-003 — 나중에 만든 PR의 병합 확인

유효한 인계가 있으면 다음 `task start`는 알려진 PR 번호를 우선 조회해야 한다. 번호가 없으면 GitHub의 PR 목록을 `state=all`, `base=dev`, `head=<origin 소유 조직 또는 계정>:<branch>`로 조회한다. 여기서는 원격 저장소의 GitHub 이름을 사용하며 로컬 작업의 `--owner`는 GitHub 조회 인자로 쓰지 않는다. 페이지별 결과를 끝까지 확인하고 시간·건수 상한이나 불완전한 응답에 닿으면 보류한다. head/base 저장소 ID, 양쪽 ref, 인계한 HEAD가 모두 일치하는 PR 번호를 찾는다. 다른 HEAD의 예전 PR은 후보에서 빠지며 정확히 일치하는 PR이 둘이면 보존한다. 목록 조회는 후보 번호만 제공한다. 유일한 후보도 `pull`로 상세 정보를 다시 확인한 뒤, 검증된 PR 정보를 담은 임시 레코드를 `mergeProof`에 전달한다. 이 함수는 `record.pr.number`를 읽으므로 `pr: null`인 원장을 그대로 넘길 수 없다. 상세 조회와 증명이 모두 성공한 뒤에만 PR 연결과 병합 증명을 원자적으로 기록한다.

원격 브랜치가 이미 삭제됐어도 인계 당시 HEAD는 PR 기록으로 대조한다. 자동 정리에는 상세 PR 상태 `MERGED`와 다음 두 가지 Git 이력 증명이 모두 필요하다. 작업을 등록할 때 저장한 `baseSha`가 GitHub가 반환한 **병합 커밋의 엄격한 조상**이어야 하고, 그 병합 커밋은 최신 원격 `dev`와 같거나 그 조상이어야 한다. 따라서 작업 시작 전에 이미 `dev`에 들어 있던 동명 브랜치·동일 HEAD의 PR 하나만 검색되더라도 보존한다. 번호를 직접 받은 경우에도 같은 기준을 적용한다. 누락된 Git 객체나 갈라진 이력으로 입증할 수 없으면 시간을 추정해서 연결하지 않는다. squash/rebase에서는 원래 PR HEAD를 병합 커밋과 구분한다.

열린 PR, 병합 없이 닫힌 PR, 후보 0개·복수, 불완전한 페이지 조회, 권한·네트워크 오류는 보존 사유다. 번호가 주어졌는데 일치하지 않으면 다른 PR로 임의 대체하지 않는다. 이 경로의 GitHub 접근은 조회만 허용한다.

### REQ-TSC-004 — 삭제 직전의 재검증과 보존

병합이 확인되면 도구는 대상 작업의 잠금 아래 현재 인계와 상태 OID, 인스턴스, 브랜치 HEAD, 경로·파일 지문, 원격 ref 재사용과 의존 PR을 다시 검증해야 한다. 현행 제거용 파일 검사와 이 호스트의 새 사용 관측을 통과해야 한다. 미커밋 변경, 보존 대상 파일, 사용 중·판정 불명, 미지원 환경에서는 보존한다. 안전한 작업 트리 제거와 등록 부재 확인 뒤에만 해당 로컬 브랜치를 지운다. `main`과 `dev`는 모든 삭제 입력에서 제외한다. Windows와 자격이 확인되지 않은 macOS에서는 기존 제거 제한을 따른다.

### REQ-TSC-005 — 보류·경합·중단 시 새 작업의 결과

이전 작업 하나의 정리가 보류되면 도구는 경로와 이유를 표시하고 독립적인 새 작업 생성을 계속해야 한다. 새 작업 자체의 검증은 그대로 적용한다. 예를 들어 GitHub PR 조회 실패는 그 후보의 정리를 보류시키지만, 원격 Git에도 연결할 수 없어 최신 `dev`를 확인할 수 없으면 새 작업 생성 역시 기존 규칙에 따라 실패한다.

`start` 둘이 겹치거나 `resume`과 정리가 경합하면 작업별 잠금과 상태 OID 비교를 이긴 전이만 효력을 가진다. 실제 취소 신호, 자기 자식 프로세스 미종료, 공용 잠금 불확실성은 호출 전체를 멈출 사유다. 정리 후보 하나의 보류와 구분해 출력한다. 이미 완료한 후보는 다시 처리하지 않는다.

중단 후에는 원장의 제거 의도와 실제 경로·Git 관리 디렉터리·등록 상태를 대조한다. 세 곳이 모두 사라졌다면 관찰한 작업 트리 제거 결과만 기록할 수 있다. **이전 호출이 작업 트리를 제거하고 브랜치 삭제 전에 끊겼다면**, 현재 이름과 SHA만으로는 그동안 같은 이름·같은 SHA로 다시 생긴 브랜치를 구분할 수 없다. 자동 경로는 여기서 남은 브랜치를 보존하고 `inspect`에 필요한 task ID와 사유를 반환한다. 운영자는 기존 복구 절차에서 남은 ref의 소유를 별도로 확인한다. 소유를 확인할 수 없으면 브랜치를 계속 보존한다.

**자동 브랜치 삭제 직전**에는 같은 task 잠금을 계속 보유한 이번 호출이 해당 인스턴스에 대해 `git worktree remove`의 성공 응답을 받고 세 곳의 부재도 확인했는지 검사한다. 이 사실은 후보별 호출 안에서만 유효하다. 앞에서 경로를 한 번 보았다는 사실, 예전 원장의 `intent/removed`, 부재만 관측한 복구, 제거 명령의 응답 유실은 이 검사를 통과시키지 못한다. 이미 들어 있던 보존 검사는 모두 계속 적용한다. 이 보장은 관리 도구의 작업 잠금을 따르는 호출을 전제로 한다.

`start`는 JSON 한 개를 반환한다. 새 작업의 생성 결과에 별도 후보 결과 목록을 붙이고, 각 행에 task ID, 확인한 PR, 작업 트리 결과, 브랜치 결과와 사유를 둔다. 생성 성공은 exit 0이며 후보 보류는 그 행에 표시한다. 생성 실패·호출 취소에도 이미 확정한 후보 효과는 반환 가능한 결과에 남긴다. 호출이 강제 종료돼 출력을 잃었을 때의 근거는 로컬 원장이다.

### 로컬 원장과 호환 설계

기존 `working → sealed` 전이와 `release` 구조를 재사용한다. 정리 대기 ref의 제안 경로는 `refs/stagekeeper/pr-closeout/released/<scope>/<task-uuid>`이며 값은 작업 원장의 현재 커밋 OID다. `start`는 현재 실행 환경에서 직접 구한 `scope`의 후보만 처리한다. 과거의 `working`, `sealed`, `cleanup-pending` 상태만으로는 정리 대상이 되지 않는다.

`installationId`는 Git 공용 디렉터리의 활성화 기록이다. macOS의 사용 검사는 **호출자의 UID**에 속한 프로세스만 관측하므로, 인계 때와 소비 때의 관측 범위도 일치해야 한다. 제안하는 macOS `scope`는 버전 표식·설치 ID·OS 장치 UUID(`IOPlatformUUID`)·동일한 실제/유효 UID를 정규화해 얻은 SHA-256 값이다. 재부팅이나 에이전트 재시작 뒤에도 같은 값을 얻을 수 있다. 장치 UUID와 UID 원문은 원장·로그·GitHub에 기록하지 않는다. CLI 옵션으로 이 값을 덮어쓸 수 없다. 이는 오인 방지용 식별이며 삭제에는 기존 소유자 인계·경로 검증·새 사용 관측이 모두 필요하다. [사용 관측의 범위](../../../scripts/pr/UPSTREAM.md)

기존 쓰기·봉인 검사를 통과했지만 자동 제거 미지원 환경이거나 장치·계정 범위를 확인할 수 없으면 사용 종료만 기록하고 `released/held/<task-uuid>`에 둔다. `release`와 `inspect`에 사유를 표시한다. 장치 신원 검증 실패로 쓰기 자체가 금지된 Windows 런타임, 취소, 미종료 자식에는 기존 중지 규칙이 먼저 적용된다. 보류 인계는 환경이 바뀌어도 자동 승격하지 않는다. 새 인계에는 재개 후 새 요청이 필요하다.

- 새 동의는 등록한 소유자가 `working`에서 인계할 때만 발급한다. 과거 `sealed`의 재전송이 새 대기 ref를 만드는 경로는 없다. 인계와 대기 ref 등록, 재개와 대기 ref 취소는 각각 기존 Git ref 트랜잭션에서 함께 수행한다. 인계할 때 PR 번호를 모르면 원장의 기존 `pr: null`을 사용한다. 번호를 제공하면 기존 `pull`이 검증한 PR 정보를 같은 트랜잭션에서 기존 `pr` 필드에 저장한다. 작업 원장의 필드나 상태 값을 늘리지 않는다.
- 후보의 task 잠금을 얻은 뒤 원장·대기 ref를 다시 읽고 실행 범위·설치 ID·작업 계보·인스턴스·인계 OID를 검증한다. 같은 task와 현재 OID를 가리키는 직접 ref가 여러 범위에 있으면 그 후보를 보존한다. 데이터에서 읽은 owner 문자열은 위임 권한이 아니다. 자동 실행 경로는 현재 범위의 정확한 task UUID를 가진 직접 ref만 받는다. `held`, 다른 범위, symbolic ref, 대상 불일치, 손상된 계보는 삭제를 승인하지 않는다. 소유자가 재개하면 상태 OID가 바뀌므로 이전 범위에 남은 대기 ref도 효력을 잃는다.
- 자동 경로가 작성하는 모든 원장 전이에서 `saveTask`의 기존 트랜잭션에 대기 ref의 이전 OID 검사를 포함한다. 최종 브랜치 삭제, 원장 완료, 대기 ref 해제를 같은 트랜잭션에 넣는다. 구버전 `resume` 등 다른 writer가 원장만 전진시키면 남은 대기 ref는 효력을 잃는다. 새 인계 시 같은 작업의 과거 ref임을 검증한 경우에만 소유자의 새 선언과 함께 두 OID를 비교해 교체한다. 손상된 ref를 자동 복구하거나 원격에 게시하지 않는다.
- `inspect`는 지정된 task UUID의 대기 ref를 읽어 결과만 반환한다. 소유자가 명시적으로 `resume`하면 기존 재개 검증을 거쳐, 원장 OID와 일치하는 유일한 직접 ref를 그 정확한 이름으로 취소한다. 이 방식으로 `held`도 철회할 수 있다. 같은 상태에 유효해 보이는 ref가 여럿이면 모호성을 보고하고 자동 삭제를 보류한다. 같은 요청을 다른 범위에서 재전송해도 새 ref를 발급하지 않는다.
- 기존 `complete`의 `MERGED` 분기에서 병합 증명을 기록하는 부분을 분리해 재사용한다. 자동 경로의 GitHub 인터페이스는 GET으로 한정한다. 열린 PR의 사전 심사나 `requestMerge`에는 연결하지 않는다. 기존 `cleanup`은 원격 보존 검사 후 작업 트리 상태를 다시 읽고, 이미 경로가 없더라도 과거 제거 의도가 있으면 브랜치 처리로 진행할 수 있다. 자동 경로에서는 **최종 브랜치 처리 지점**에 위의 호출별 제거 확인을 적용한다. 직접 실행한 기존 `pr complete/cleanup`과 명시적 외부 제거 인수는 자체 계약을 따른다.
- `release` 재전송은 최초 봉인 레코드의 `release.requestId/sourceState/head/instance`, owner·task, 선택 PR을 원래 입력과 대조한다. 응답을 잃은 뒤 같은 입력을 보내도 동의는 한 번만 발급된다. 이미 취소·완료·대체된 인계의 재전송은 과거 결과 또는 만료 사유를 반환하며 대기 ref를 되살리지 않는다. 같은 요청 ID로 입력을 바꾸면 거부한다. 판독 상한 안에서 원래 이력을 입증할 수 없으면 보존한다.
- v1의 `requests`는 허용된 연산 네 종류와 최대 256건을 검증한다. 새 공개 동사 `start/release`를 여기에 쓰지 않는다. 병합 증명과 동시에 실행 가능한 자동 `cleanup` 요청 ID 하나를 발급한다. 해당 전이에서 추가된 요청은 하나뿐이며 원래 인자·예상 OID는 그 전이와 부모 원장에서 복원 가능해야 한다. 재시도에는 그 ID와 서명을 재사용하고 매 호출의 새 OID는 ref 비교에만 쓴다. 공개 `cleanup` 호출을 이전 소유자 이름으로 대신 실행하지 않는다. 같은 보류 상태를 다시 관측했을 때는 결과만 보고한다. 효과나 사유가 바뀌지 않은 호출이 요청 슬롯과 원장 이력을 소진하지 않아야 한다.

### 시작 지연과 잠금

공통 인자·실행 위치·관리 소스·활성화·장치 신원 검사를 통과하면 현재 범위의 대기 ref가 있는지 로컬에서 확인한다. **후보가 0개면 기존 `create`를 한 번 호출하고 끝낸다.** 생성에 필요한 원격 ref 조회와 전체 등록 작업의 충돌 검사는 그 호출이 소유한다. 이 경우 정리용 사전 조회·전체 작업 원장 순회·마지막 검사 위치 기록을 추가하지 않는다. 목록을 읽은 직후 들어온 인계는 다음 호출에서 확인할 수 있다.

후보가 있으면 삭제 효과에 앞서 보호 원격 ref와 새 branch/path 충돌을 확인한다. 후보마다 task 잠금을 따로 쓰고 공용 잠금 안에서 GitHub를 조회하지 않는다. 정리 시도 후 생성 시점에 최신 원격 `dev`와 충돌 여부를 다시 검증한다.

호출당 최대 4개 후보를 순차적으로 검토하는 것을 초기 설계값으로 둔다. 다음 호출은 직전 시도한 task ID 다음부터 순환한다. 저장하는 마지막 ID는 순서 선택에만 쓰며, 유실되면 처음부터 읽어도 권한 판단은 같다. 동시 호출의 마지막 위치 갱신은 짧은 공용 잠금 안에서 수행하고 개별 후보는 task 잠금 아래 다시 검증한다. 후보가 0개면 **정리 목적**의 GitHub 요청은 0회다.

20초는 **이번 호출에서 후보를 찾아 검증하고 제거에 착수할 수 있는 시간**의 초기 설계값이다. 후보 전체에 단조 시계 기준 마감 하나를 사용한다. 조회 중에는 남은 시간을 GitHub와 원격 Git 명령에 전달하고, 제거 의도를 저장하는 트랜잭션을 시작하기 직전에 다시 확인한다. 그 전에 만료되면 대상과 브랜치를 보존한다.

조회용 기한은 해당 읽기 구간 안에서만 적용하고 예외 경로에서도 복원한다. 기존 `runCommand`는 `ctx.deadline`을 로컬 Git 명령에도 적용하므로, 만료된 기한이 원장 쓰기·제거 명령·잠금 정리·새 작업 생성으로 넘어가서는 안 된다. 제거 의도 트랜잭션에 이미 착수했다면 같은 후보의 결과 기록과 **브랜치 삭제 전 두 번째 원격 보존 검사**는 기존 명령별 제한 안에서 마친다. 두 번째 검사가 실패하면 확인된 작업 트리 결과를 보고하고 브랜치는 보존한다. 예산 만료 후 다음 후보에 착수하지 않는다. 사용자 취소와 미종료 자식에 대한 중지 규칙은 전체 호출에 적용한다. [명령 실행 범위](../../../scripts/pr/git-workspace.mjs) · [제거 순서](../../../scripts/pr/index.mjs)

따라서 20초는 전체 응답시간 보장이 아니다. 구현에서 동일한 작업 목록에 대해 후보 0개·보류 누적·병합 1건의 벽시계 시간과 원격 요청 수를 생성 전용 명령과 함께 기록한다.

## Safety Analysis

GitHub에서 PR을 찾아도 유효한 로컬 인계가 없으면 어떤 파일도 지울 수 없다. 읽기 전용 `pr inspect --task <id>`는 대기 ref의 부재, 현재 범위에서의 일치, 다른 범위 또는 `held`, 원장 OID 불일치를 구분한다. 이 결과는 삭제 전 재검증을 대체하지 않는다. 인계가 있어도 PR 증명과 삭제 직전 사용 관측이 필요하다. 자동 경로가 `--usage-ended`를 나중 작업의 소유자 이름으로 만들어 전달하는 구현은 이 계약을 위반한다. 재개 또는 인계와 무관한 상태 변경 이후에는 이전 인계를 사용할 수 없다.

장치·계정의 일치는 두 호출의 관측 범위를 확인할 뿐이다. 소유자가 다른 계정·호스트의 공유 사용 종료를 확인할 수 없으면 `--usage-ended`를 선언하지 않고 작업을 유지한다. 인계 후의 모든 접근을 자동으로 감지할 수도 없으므로 **작업 트리를 다시 사용하기 전에 리뷰 재개 명령이 성공했는지 확인하는 순서**를 운영 지침과 인수 시험에 넣는다. [사용 관측 및 복구 규칙](../../architecture/verification.md#작업-브랜치-정리)

### VFY-TSC-01 — 시작·인계·재개의 호환

실제 CLI 진입점으로 `task complete` 거부와 JSON·종료 코드를 검사한다. 이전 판독기는 변경 전 `84d8016`의 판독 규칙을 고정한 대조군을 쓴다. 응답을 잃은 동일 요청, 같은 ID의 변경된 PR, 취소 후 재전송, 같은 SHA의 새 인계를 비교해 대기 ref와 원장의 OID를 직접 단언한다.

같은 Git 공용 디렉터리·설치 ID·task·HEAD를 고정하고 발급·소비 환경만 바꾼다. 같은 장치·계정의 새 세션은 기존 인계를 찾고, 다른 장치에 같은 UID를 준 경우와 같은 장치에 다른 UID를 준 경우에는 해당 후보의 원격 조회·제거가 모두 0건이어야 한다. 식별 실패에 따른 `held` 기록, 판독 전용 런타임의 쓰기 0건, 재개 후 재발급, 장치·계정 원문 비노출도 확인한다. 격리 시험에는 합성 식별값을 쓴다. 지원 macOS의 별도 프로세스 두 개에서 같은 설치·계정의 범위가 일치하는지 값의 일치 여부만 검증한다. 자동 제거 자격 판정은 기존 native 시험을 함께 사용한다.

### VFY-TSC-02 — 나중에 만든 PR과 원격 쓰기 0건

- verifies: REQ-TSC-003, REQ-TSC-004

PR 없이 인계 → 웹에서 PR 생성·병합에 해당하는 대역 응답 → 원격 작업 브랜치 삭제 → 다음 작업 시작 순서로 재현한다. 로컬 저장소에 실제 병합 이력을 구성해 일반 병합과 squash/rebase를 검증한다. 지원 환경 대조에서 원래 작업의 경로·등록·로컬 브랜치만 사라지고 새 작업은 생성돼야 한다. 열린 PR, 병합 없이 종료, 포크, 다른 base, SHA 불일치, 모호한 결과, `dev` 이력 밖 병합 커밋도 대조한다. **모든 경우 GitHub 변경 요청과 원격 ref 변경은 0건**이어야 한다.

기존 `mergeRemote()`는 `dev`를 PR HEAD로 옮긴다. 이 모형과 별도로 squash/rebase 대조군에는 **원래 HEAD가 dev의 조상이 아니며, GitHub가 보고한 별도 커밋만 dev의 조상**인 Git 그래프를 만든다. 후보가 둘째 페이지에 있는 경우, 예전 다른 SHA와 같은 SHA의 중복 후보, 페이지 중단 및 목록·상세 불일치도 검증한다. fixture는 모든 GitHub 메서드·경로를 기록해 GET 이외 호출을 거부하고, 사람의 병합을 준비한 직후와 도구 실행 직후의 bare origin ref 전체를 비교한다. `puts === 0` 하나만으로 원격 무변경을 판정하지 않는다.

특히 **검색 결과가 딱 하나인 과거 PR**을 대조한다. 동일 저장소·브랜치·HEAD·병합 PR·최신 `dev`를 고정하고 작업의 출발 커밋만 바꾼다. 출발 커밋이 병합 커밋의 엄격한 조상이면 다음 검사를 진행한다. 두 커밋이 같거나 병합 커밋이 출발 커밋에 이미 포함되거나 이력이 갈라졌으면 브랜치와 작업 트리가 모두 남아야 한다. PR 번호를 명시한 경우와 검색으로 찾은 경우에 같은 표를 적용한다.

### VFY-TSC-03 — 보존 경계와 새 작업 생성

- verifies: REQ-TSC-004, REQ-TSC-005

인계되지 않은 기존 작업, dirty·ignored 사용자 자료, 사용 중·미확인, 다른 인스턴스, 재사용한 경로·브랜치, 의존 PR과 Windows 보존을 확인한다. 정리 보류 사유와 새 작업 생성 결과를 독립적으로 단언한다. PR 조회만 실패하는 경우와 원격 `dev` 자체를 확인할 수 없는 경우를 구분한다. 사용 중인 실제 사용자 작업 트리로 삭제를 시험하지 않는다.

가짜 단조 시계와 요청 로그로 0·1·5개 후보를 대조한다. 빈 목록의 정리 요청 0건, 첫 네 후보가 계속 보류돼도 다섯째가 다음 호출에서 검사되는지 확인한다. 제거 의도 저장 직전의 예산 만료는 두 자원 보존과 정상 생성을, 작업 트리 제거 직후의 만료는 결과 기록과 두 번째 원격 보존 검사 실행을 단언한다. 후자의 검사가 성공하면 같은 호출에서만 브랜치 제거를 마친다. 검사 실패 시에는 작업 트리 제거와 브랜치 보존을 각각 보고한다. 두 경우 모두 추가 후보 조회는 없어야 한다. 명시적 취소나 미종료 자식에서는 새 생성을 시작하지 않고, 독립적인 후보 조회 실패에서는 생성 결과와 보류 결과가 함께 나와야 한다. 반복 보류가 기존 256건 요청 한도를 잠식하지 않는지도 검사한다.

기존 작업 기록은 있지만 현재 범위의 대기열은 빈 두 동등한 fixture에서 `pr create`와 `task start`를 각각 실행한다. Git trace로 원격 `ls-remote`, `fetch`, 전체 task ref 열거 횟수가 생성 전용 호출과 같은지 확인한다. 정리용 GitHub 요청은 0이고 새 작업은 양쪽 모두 정상 등록돼야 한다. 시간 측정만으로는 불필요한 중복 호출을 잡을 수 없다.

### VFY-TSC-04 — 경합·중단·재실행

- verifies: REQ-TSC-004, REQ-TSC-005

동시 `start` 두 개, 같은 HEAD의 `resume` 선점, 제거 의도 기록 전후와 작업 트리 제거 직후 중단을 시험한다. 원장·대기 ref 중 하나의 예상 OID만 바꾼 경우에도 두 ref와 브랜치의 최종 트랜잭션 전체가 실패해야 한다. 실제 프로세스를 끊어 task 잠금만 남으면 자동 `recover-guard` 호출 0건과 해당 후보 보류를 단언한다. 공용 잠금까지 남는 경우에는 새 생성도 중단해야 한다. 명시적 기존 잠금 복구 후 경로·등록이 사라진 상태에서 같은 SHA의 동명 브랜치를 다시 만들고 다음 `start`가 이를 보존하는지 확인한다. 정상 완료된 요청의 재전송과 경로 재등장도 서로 구분한다.

사전 확인에서 작업 트리가 있었지만 내부 보존 검사 후 다시 읽을 때 이미 사라진 경우, 또는 제거 명령의 성공 응답을 잃고 부재만 확인한 경우에도 자동 브랜치 삭제 횟수는 0이어야 한다. 한 후보의 정상 제거 직후에 이 사례를 배치해 앞 후보의 성공 정보가 다음 후보로 넘어가지 않는지도 확인한다. 기존 명시적 외부 제거 인수와 `pr cleanup`의 성공 대조군은 유지한다.

구현 시 집중 시험과 문서 검사는 아래 명령으로 실행한다. 기존 아키텍처·lint·타입·테스트·빌드 검증은 [저장소 검증 지침](../../architecture/verification.md)을 따른다.

## Risks and Rollback

구현과 격리 검증 결과는 아래 완료 기록에서 확인할 수 있다.

문제가 발견되면 새 작업 시작 지침을 생성 전용인 `pr create`로 되돌리고, `task start`의 자동 정리 호출을 비활성화한다. 인계·제거가 진행 중인 작업은 최신 도구의 `inspect`와 기존 복구 절차로 작업별 확인한다. 원장과 대기 ref를 일괄 삭제하지 않는다. 회귀 시험은 자동 호출 중단 후 생성·조회만으로 기존 작업에 삭제 효과가 없는지 확인한다.

이미 지워진 로컬 파일은 코드 롤백으로 복원되지 않는다. `dev`에 보존된 커밋과 원장에 고정된 객체는 Git 자료 복구에 쓰일 수 있지만, 미추적 자료의 복구 수단이 될 수는 없다. 미추적·ignored 사용자 자료와 파일 지문을 제거 직전에 검사하는 이유다.
